About The Project & Viva Questions

A complete technical guide to help explain design choices and code mechanics during evaluation.

1. Project Purpose & Architecture

The Smart Appliance Service Request System addresses the operational bottlenecks of manual phone-call appliance booking. It provides an asynchronous digital interface allowing customers to report problems, attach photographic evidence of faulty parts, pick convenient repair slots, and receive auto-incrementing tracking IDs (e.g. SR-2026-001).

The architecture is built completely on frontend technologies (HTML5, CSS3, Vanilla JavaScript) utilizing the browser's HTML5 LocalStorage API for persistent data management and the FileReader API for Base64 Data URL conversions.

2. Frequently Asked Viva Questions & Answers

Q1: Why did you not use a backend like Node.js, PHP, or Python?

Answer: This project is intentionally developed with pure client-side web technologies (Vanilla JavaScript and LocalStorage) to demonstrate core DOM manipulation, event-driven state handling, file streaming via FileReader, and local data persistence without reliance on third-party frameworks or external server dependencies.

Q2: How does the image upload feature work without an external database or S3 bucket?

Answer: The file is processed locally using the JavaScript FileReader interface through readAsDataURL(). It converts the image binary stream into an alphanumeric Base64 Data URL string. This string is then stored directly within the JSON entity in localStorage and assigned to an <img src="..."> element for zero-latency rendering.

Q3: How do you prevent LocalStorage quota overflow?

Answer: Standard browser LocalStorage is capped at approximately 5MB. To avoid quota overflow errors, strict client-side validation enforces allowed image file types (JPG, JPEG, PNG) and caps upload size at 2MB.

Q4: How does the sequential Request ID generator guarantee uniqueness?

Answer: A dedicated sequence counter (smart_appliance_counter) is stored in LocalStorage. Whenever a new form submission triggers generateServiceRequestId(), the current year is retrieved via new Date().getFullYear(), the counter increments atomically, is padded to 3 digits (e.g., 001, 002), and produces SR-2026-xxx.

Q5: How does the 5-stage status timeline update dynamically?

Answer: The timeline function in details.js checks the current status against an ordered array of milestones (Request Submitted → Under Review → Technician Assigned → Service in Progress → Completed). Any milestone whose index is lower than the active stage receives the .done CSS class (green checkmark), while the active milestone receives the .active CSS class (blue pulsing indicator).

3. Project Scope, Limitations & Future Enhancements

Academic Project Limitations

  • Data is restricted to the current browser profile (LocalStorage).
  • No live gateway for payments or credit card processing.
  • Authentication is role-simulated without server session cookies.
  • No real SMS/Email dispatching to technicians.

Future Enhancements for Real-World Deployment

  • Integration of a Node.js/Express REST API with PostgreSQL/MongoDB.
  • Geolocation API & Leaflet maps for live technician tracking.
  • Integration of cloud storage (AWS S3 or Cloudinary) for high-resolution photos.
  • Twilio/SendGrid API for automated SMS and email notifications.
